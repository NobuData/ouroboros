**Research**, at `/research`, is where you ask Ouroboros a question instead of handing it a
ticket. Open it from **Research** in the sidebar.

A **research investigation** reads the outside world, and your own code and history, to answer
a question. Every claim it makes cites a source it read, and its findings can become drafted
tickets for the loop to pick up.

<Screenshot id="user-guide.research" />

:::info[The page is arriving in parts]

The page's frame is here, and so is its composer: you can
[start an investigation](#starting-an-investigation) and follow it as it runs. The other five
regions say what they will hold and are filled in by later releases — until the brief view
arrives, a finished investigation's **View brief ↑** lands on the **Featured brief** region's
placeholder.

:::

## The page

The head states what the page is for:

> **Ask a hard question. Get an evidenced answer — and the tickets to act on it.**

Two buttons sit beside it:

- **Research library** opens `/research?view=library`: the page opens scrolled to
  **Investigations**, which is outlined until you move on, and the card shows every
  investigation with its filters — see [Investigations and the library](#investigations-and-the-library).
  A link to that address opens the same way; any other value of `view` opens the page from its
  top.
- **New investigation** scrolls to **Start an investigation** and outlines it. It opens no
  dialog: the composer is part of the page.

Below the head, the page has six regions:

| Region | What it will hold |
| --- | --- |
| **Start an investigation** | The composer: your question, its kind, how deep to go and which tools to use, with an estimate before you start — see [Starting an investigation](#starting-an-investigation) |
| **Research tools** | Each [research tool](#research-tools), with its health and how to enable it |
| **Regression watch** | Drift against each release's baseline, from detection to a merged fix |
| **Featured brief** | A cited brief, with its capability matrix and numbered sources |
| **Roadmap pipeline** | A brief's roadmap document, and the issues filed from it |
| **Investigations** | Every investigation, and the library: the same list filtered by kind, status and quarter — see [Investigations and the library](#investigations-and-the-library) |

On a wide screen **Start an investigation** sits beside **Research tools** and **Regression
watch**, and the other three run the full width below. On a narrow screen all six stack in that
order.

### Who can start an investigation

Everyone in the workspace can read the page and open the library. Starting an investigation
spends the workspace's money, so **New investigation** is switched off for a **Viewer**. Hover it
to read why: *Starting an investigation is for workspace owners, admins and members — a viewer
can read the research.* See [Roles](../administration/roles.mdx).

A workspace chooses the lowest role that may start one. The setting has two values:

| Setting | Who may start an investigation |
| --- | --- |
| `member` | Owners, Maintainers and people holding the [`member` role](../administration/roles.mdx#the-member-role). This is what a workspace uses until it chooses. |
| `admin` | Owners and Maintainers only. |

A Viewer can never start one, whichever value is set. An Owner or a Maintainer changes the
setting — see [Who may start an investigation](../administration/research.mdx#who-may-start-an-investigation).
<Since version="0.41.8" module="ouroboros-rest" />

A start that is not allowed is refused with `403 forbidden`, and the refusal lists the roles
that would have been enough.

### Who can cancel an investigation

An investigation that is queued or running can be cancelled by:

- **the person who started it**, whatever their role is now;
- an **Owner** or a **Maintainer**.

Anyone else is refused with `403 investigation_cancel_forbidden`. This rule is fixed: the
setting above does not change it.

Cancelling keeps what the investigation gathered:

- A **queued** investigation is cancelled at once.
- A **running** one finishes the step it is on, then stops. Until it has stopped its status
  reads **cancelling**.
- Its sources stay in the list and are still counted, and it records what the partial run
  spent. A cancelled investigation is listed as **cancelled** and does not count as active.

An investigation that has already finished cannot be cancelled (`409
investigation_not_cancellable`).

## The four kinds of investigation

| Kind | What it answers |
| --- | --- |
| **Bug root cause** | Why a bug happens: a root-cause brief for a bug fix |
| **Regression forensics** | What changed between a good version and a bad one |
| **Roadmap & improvements** | What to build next: a product roadmap and improvement proposals |
| **Gap analysis** | How a project compares with its competitors |

## Starting an investigation

**Start an investigation** is the card at the top left of the page. It asks for a question, a
kind, a depth and the tools to use, tells you what the investigation will cost before you start
it, and then follows the run in place. <Since version="0.146.0" module="ouroboros-ui" />

<Screenshot id="user-guide.research.composer" />

### The question

Write it in the field labelled **Ask like you'd ask a principal engineer**. Say what you want
to know and what would count as an answer; the example in the field, *Why are we losing
autonomous-docking deals?*, is the shape. **Start investigation ⟳** stays off until the question
has some text.

### The kind

Choose one of the four kinds with the segmented control under the question. Choosing a kind
turns on the tools its playbook uses by default and changes the **Deliverable** line, which
says what the investigation will leave behind and ends in [Planning](./planning.mdx), where
drafted work goes:

| Kind | Tools on by default | Deliverable |
| --- | --- | --- |
| **Bug root cause** | Codebase & git mining, Issue & PR history index, Build & test telemetry | cited research brief → drafted fix ticket in Planning |
| **Regression forensics** | Codebase & git mining, Build & test telemetry, Issue & PR history index | cited research brief → drafted fix ticket in Planning |
| **Roadmap & improvements** | Issue & PR history index, Web search & page reader, Competitor tracker | cited research brief → roadmap document → drafted epics & tickets in Planning |
| **Gap analysis** | Web search & page reader, Competitor tracker, Codebase & git mining, Issue & PR history index, Build & test telemetry | cited research brief → capability matrix → drafted epics & tickets in Planning |

The page opens on **Gap analysis**. A workspace owner can add kinds; one that was added appears
after the four built-in ones.

### The depth

**Depth** is a menu beside the kinds. Each depth runs the investigation's research loop for a
set number of rounds, and each option in the menu shows what that depth would cost for the
tools you have on — the same figures the estimate line shows once you choose it:

| Depth | Rounds | Synthesis passes |
| --- | --- | --- |
| **Quick** | 1 | 1 |
| **Standard** | 2 | 2 |
| **Deep dive** | 4 | 4 |

The page opens on **Deep dive**.

### The tools

The **Tools:** row has one chip per [research tool](#research-tools). A chip with a ✓ is on; a
chip with a · is off; press a chip to switch it. At least one tool must be on.

A tool this deployment has no adapter for yet — **Docs, standards & papers**, whose adapter is a
later release — is drawn faded and cannot be switched on. Hover it to read why, and press it to
go to **Research tools**, where tools are enabled. Whether a tool that *is* available is healthy
is shown in **Research tools**, not here.

### The estimate line and the researcher

Above **Start investigation ⟳** the card prints an estimate, for example
`est. 40–60 sources · ~$6`: how many cited sources the investigation is expected to gather, and
roughly what its model calls will cost. It is recomputed every time you change the kind, the
depth or a tool, and it is never a guess: the source range comes from the depth and the tools,
and the dollar figure from the per-token price of the model that will run the research.

**When no dollar figure shows**, the line reads `est. 40–60 sources` alone. That means the
researcher's model has no per-token price in this workspace — a seat-priced or unpriced model —
so there is no cost Ouroboros can honestly compute. You can still start the investigation; its
spend is simply unknown in advance. The line never shows `$0` in place of *unknown*.

The pill in the card's corner, `researcher: researcher-long-ctx`, names the model alias that
will run the investigation: what the workspace's [routing](./models.mdx) resolves the `research`
task kind to right now, fallback included. If it changes in Models, the pill changes here. When
it reads `researcher: none routed`, nothing in the workspace's routing can run the research and
**Start investigation ⟳** stays off until that is fixed.

While the estimate is being recomputed the line is dimmed and the button waits; if the estimate
cannot be read at all the line says *estimate unavailable* and nothing can be started.

### When Start is off

**Start investigation ⟳** is switched off, with the reason as its tooltip, when:

| Reason | What to do |
| --- | --- |
| *Starting an investigation is for workspace owners, admins and members — a viewer can read the research.* | Ask for the `member` role — see [Who can start an investigation](#who-can-start-an-investigation) |
| *This workspace lets only owners and admins start an investigation.* | Ask an owner or admin to start it, or to change the setting |
| *Write the question first.* | Type the question |
| *Turn on at least one research tool.* | Press a chip |
| *No researcher is routed: the research task kind resolves to nothing usable. See Models.* | Fix the `research` route in [Models](./models.mdx) |
| *The estimate is still being read.* | Wait a moment |
| *The estimate could not be read, so nothing can be started.* | Reload; if it persists, the research service is unavailable |

**New investigation** in the page head is switched off for the first two reasons too, with the
same words.

### While it runs

Pressing **Start investigation ⟳** starts the investigation and turns the card into its progress
view, in place. It shows the kind, the investigation's number (`RS-128`), your question, and a
line that updates as the run works:

- a status pill — **queued**, then **running**; **cancelling** if you asked it to stop;
- the sources gathered so far, for example `12 sources`, counting up as the ledger grows;
- the spend so far, for example `$1.40` — what the run's model calls have cost. When nothing
  priced has run yet, or the researcher is unpriced, no figure is shown at all;
- the round being worked, for example `round 2 of 4`, and the estimate the run started under,
  so the two can be compared.

**Cancel** stops the run. The person who started it, and any owner or admin, may cancel; for
anyone else the button is off and says who may. A cancelled run is kept, not discarded: the
card reads **cancelled** with the sources it gathered and what it spent, and the investigation
stays in the list — see [Who can cancel an investigation](#who-can-cancel-an-investigation).

When the run finishes the pill reads **✓ brief ready** and the card offers **View brief ↑**,
which takes you to the **Featured brief** region. A run that could not finish reads **failed**
with the reason under it. **Start another** returns the card to a blank question with your kind,
depth and tools kept.

## Research tools

Investigations read through **research tools**, which a workspace owner or admin enables. Each
tool reports its own health, so a broken setup shows before an investigation depends on it.

| Tool | What it does | What it cites | Setup |
| --- | --- | --- | --- |
| ◍ **Web search & page reader** | Searches the web, then reads whole pages: the main content, without navigation, banners or footers | Each search result, with its snippet. Each page read, at the address it was read from, with an excerpt and a fingerprint of its content. | Nothing, on a deployment that runs SearXNG. A hosted search provider needs a key. See [Research tools](../administration/research.mdx). |
| ⌖ **Competitor tracker** | Watches your rivals' release notes, changelogs, GitHub releases and feeds on a schedule, and keeps every change | Each change, as the archived difference between two dated snapshots | An owner or admin adds rivals and their watches. See [Competitor watch](#competitor-watch). |
| ⌥ **Codebase & git mining** | Reads the workspace's enabled repositories: who last changed a line and when, how often a file changes, what moved between two versions, a module's dependencies, and which commit broke a test | Each answer, at the exact commit it was read at, so it can be read again and give the same answer. A bisect's culprit, with the build-farm jobs that proved it. | Nothing beyond enabling the repository, with **Enable *repository* →** on [Get Started](./getting-started/wizard.mdx). A private repository also needs the workspace's backlog token. See [Code & git mining](#code--git-mining). |
| ▤ **Issue & PR history index** | Searches your workspace's own history: every ticket from every connected ticket source, your pull requests, and document sets an owner imports, such as churn interviews. It also counts them, by label, period, kind, repository or set. | Each ticket, pull request and imported document it read, at an `issue-index://` address, with the passage that matched | Nothing beyond a connected ticket source. An owner imports document sets. See [Issue & PR history](#issue--pr-history). |
| ∿ **Build & test telemetry** | Reads what Ouroboros already measures in your workspace: Insights metrics, test results and flake scores, HIL bench measurements, runs and token usage. It reads a metric over a window, compares two windows, and never changes anything. | Each figure, at a `telemetry://` address that holds the whole question — the metric and the exact dates — so it can be asked again and give the same answer | Nothing. See [Build & test telemetry](#build--test-telemetry). |

The web tool's row reads *search API + full-page extraction, robots-aware*. The competitor
tracker's row counts what is watched, for example *4 rivals watched · release notes, changelogs,
filings*. A rival counts once it has an enabled watch that can be read. The code tool's row names
the repositories it reads, for example *blame, bisect, dependency graph over helios-firmware*.
The history index's row counts what it holds, for example *389 issues · 12 pull requests ·
Support churn interviews Q2*. The telemetry tool's row counts what there is to read, for
example *8 HIL measurements · 24 insights metrics · 63 test cases*.

### Pages the web tool does not read

The web tool respects what a site asks. When it will not read a page, the investigation records
the skip with a note saying why, and carries on. The skip is never hidden.

- **robots.txt disallows the page.** The note names the rule, for example
  `Disallow: /private/`.
- **The page is a PDF.** The note reads *papers tool arrives in v2*.
- **The page is not text**, such as an image. The note names the content type.

A page that fails to load, because the site is down or slow, is not a skip. The investigation
may try it again.

## Competitor watch

The competitor tracker keeps an eye on your rivals so an investigation can cite what they
shipped, and when. It does not cite a live page, which a rival can reword tomorrow. It cites the
**change** between two snapshots it archived, with both dates behind it.

### Rivals and watches

A **rival** is a competitor by name, such as *Skylink*, with an optional site, other names it
goes by, and notes. An investigation can name a rival by any of those names.

A **watch** is one source of a rival that the tracker checks on a schedule:

| Source kind | What is watched | How it is read |
| --- | --- | --- |
| `release_notes` | A release-notes page | The page, optionally narrowed to one region |
| `changelog` | A changelog page | The page, optionally narrowed to one region |
| `page` | Any other page | The page, optionally narrowed to one region |
| `github_releases` | A GitHub repository's releases, such as `https://github.com/skylink/firmware` | GitHub's API, with the workspace's GitHub token |
| `rss` | An RSS or Atom feed | Each item's title, date, link and summary |
| `filings` | A rival's filings or investor page | Not read yet. It is counted on the card and waits for the filings reader in a later release. |

A page watch can carry a **selector**, a CSS selector such as `main .release-list`, that names
the region to watch. Without one, the tracker watches the page's main content. Narrowing to a
region is what keeps a new banner or a footer's date from counting as a change. GitHub releases
leave out drafts and mark pre-releases.

### Cadence

Each watch is checked **hourly**, **daily** (the default) or **weekly**. Checks are spread out,
each landing within a quarter of the cadence either side, so a restart or a hundred new watches
never check everything at once. A check that fails is tried again sooner, within the hour.

### What a check finds

- **A change.** The tracker archives a snapshot of the region and the difference from the last
  one. Added lines start with `+`, removed lines with `-`. This is what an investigation cites.
- **No change.** Nothing is archived, so an unchanged page never shows up as a change.
- **A page that needs JavaScript.** Some pages show nothing until a script runs. The tracker
  marks the watch with the note *the page renders its content with JavaScript — it needs the
  render tier, arriving in v2*. It never archives an empty snapshot.
- **A page it may not read.** If robots.txt forbids it, the watch says so and names the rule.
- **A failure.** The watch keeps a note saying why, such as *the selector matched nothing on the
  page*.

### Citing a change

During an investigation, the loop asks the tracker for a rival's **changes** over a window, 90
days by default, or for the **latest** change of one source kind. Each change becomes a source
in the brief, titled like *Skylink · release notes · changed 2026-10-01*. Its excerpt is the
difference itself.

## Code & git mining

The code & git mining tool answers questions about your own code from its git history. It needs
no model and makes no guesses: the same question at the same commit always gets the same answer.
It reads the repositories enabled for the workspace, and never changes them.

An investigation names a repository as `owner/name`, such as `acme-robotics/helios-firmware`, or
by its name alone when only one enabled repository has it. A question is asked at a branch, a tag
or a commit; the default branch when none is named.

### What it can answer

| Question | What you get |
| --- | --- |
| **Blame** a file's lines, such as `src/dock/dock_ctrl.c` lines 200-230 | Who last changed each line, in which commit, and how long the lines have gone unchanged, for example *unchanged in 14 months* |
| **History** of a file, a directory or a symbol over a window, 90 days by default | Each change with its author and the lines added and removed, how many people made them, and how often it changes per month |
| **Changed between** two versions, such as `v2.0.4` and `nightly`, optionally inside one directory | Every commit in between that touched it, and the files they touched, most-changed first |
| **Dependency graph** of a directory | Which files include or import which, rolled up to directories, and what it uses from outside the repository |
| **Bisect** a test between a good version and a bad one | The commit that broke it, found by building commits on the build farm. See [Bisect](#bisect). |

"Unchanged in 14 months" is measured to the date of the commit the question was asked at, not to
today, so a citation of it stays true.

### Dependency graphs

The graph is read for three stacks: **C and C++** (`#include`), **Python** (`import`) and
**JavaScript and TypeScript** (`import`, `export … from` and `require`). The stack is the language
in the repository's detection card, **We already figured this out**, on
[Get Started](./getting-started/wizard.mdx#2-pick-a-repo).

For any other stack, or a directory with no source files of its stack, the tool answers
**unsupported** and says why, for example *dependency graphs are read for C/C++, Python and JS/TS;
acme-robotics/ground-station is detected as Rust*. It never answers with an empty graph, which
would read as "no dependencies".

### Bisect

A bisect finds the commit that broke a test. You give it:

- a **good** version, where the test passed, such as `v2.0.4`;
- a **bad** version, where it fails, such as `nightly`;
- the **test**, by name, such as `hil:hover_drift`, and the command that runs it;
- the build-farm **pool** to run it on.

It lists the commits from good to bad along the bad version's main line, then runs the test on
the build farm at the middle one. A job that succeeds marks that commit good; a job that fails
marks it bad. Each answer halves what is left, so a bisect over *n* commits takes at most
⌊log₂ *n*⌋ + 1 farm jobs: nine jobs for 300 commits.

A bisect runs for as long as its builds take, and it survives restarts. Each step's result is
saved as it arrives, and a bisect carries on from the last saved step rather than starting
again. Asking the same question again returns the bisect already running, or already finished.

| Outcome | Means |
| --- | --- |
| **Converged** | The culprit commit was found. It is cited with the farm jobs that proved it. |
| **Inconclusive** | The only candidate commit built good, so the failure did not reproduce |
| **Failed** | A step could not be decided, for example its farm job was canceled or the farm refused it. The note says which. |
| **Canceled** | Someone stopped it. Its running farm job is canceled too. |

### Citing code

Every answer is cited at the exact commit it was read at, so anyone can read the same thing
again. A blame is cited by the file and the lines, a bisect by its culprit and the farm jobs that
proved it.

## Issue & PR history

The issue & PR history index is your workspace's own memory, searchable: what was reported, what
was changed, and what people told you.

It reads three things:

- **Tickets** from every connected [ticket source](../administration/sources.mdx).
- **Pull requests** mirrored from your git host.
- **Imported document sets**, such as a quarter's churn interviews, which a workspace owner
  imports. See [Importing a document set](../administration/research.mdx#importing-a-document-set).

The index does not know which tracker a ticket came from. A ticket from one tracker is searched,
counted and cited exactly like a ticket from another, so changing tracker changes nothing in
your investigations.

### What the index can answer

| Question | What you get |
| --- | --- |
| **Search** for words, such as *docking abort* | The best matches first, each with the passage that matched. Entries that mention every word come before entries that mention only some, and a match in a title counts for more than one in the text. |
| **Get** one entry by its address, such as `issue-index://support/churn-2026-q2` | The ticket, pull request, document set or document at that address |
| **Aggregate**: count entries by **label**, **period** (day, week or month), **kind**, **repository** or **set** | The counts, largest first, or oldest first for a period. An aggregate can also count only the entries that mention given words. |

Search and aggregate can be narrowed by kind (ticket, pull request, document or document set),
label, date, repository and set. A *set* is one ticket source or one imported document set.

Search understands word forms: *docking* also finds *dock* and *docked*.

An aggregate looks back 90 days unless the investigation names another window or a start date.
It counts tickets, pull requests and documents. An entry with two labels is counted under both
labels, and once in the total.

When nothing matches, the tool answers with nothing rather than with an empty result. An
investigation never sees another workspace's history.

### Citing history

Every entry an investigation reads is cited at an `issue-index://` address:

| Entry | Address | Example |
| --- | --- | --- |
| Ticket | The ticket source's name, then the ticket's identifier in its tracker | `issue-index://support/SUP-3001` |
| Pull request | The source's name, `pull`, then its number | `issue-index://github-acme-robotics/pull/514` |
| Document set | Its collection, then its name | `issue-index://support/churn-2026-q2` |
| Document | Its set's address, then its key | `issue-index://support/churn-2026-q2/acct-01` |

A ticket source's name is written in lower case with hyphens, so *GitHub · acme-robotics* becomes
`github-acme-robotics`.

A search hit is cited with the passage that matched. A count is cited by the newest entries in
its largest groups, so a claim about how many tickets mention something points at the tickets
behind it.

## Build & test telemetry

The build & test telemetry tool lets an investigation quote your own numbers: how a metric
stood over a stretch of time, how a test has been doing, how one window compares with another.
It reads what Ouroboros already records and collects nothing new. It needs no setup and no
credential, and it never changes what it reads.

### What telemetry can answer

| Question | What you get |
| --- | --- |
| **A metric over a window**, such as merge rate over the last 30 days | The figure, its unit, and what it rests on: how many samples, pull requests or days. For a measurement, the median and the spread too. |
| **Two windows compared**, such as this week against the `v2.0.4` baseline | Both figures with their sample counts, and the difference with its sign and unit, for example *+14% (+4.34 cm)* |
| **A test's history**, for one test case or a whole suite | How often it passed, failed or was flaky, how many retries it took, and its current flake score and quarantine state |
| **Runs or token usage per day** | The days that had any, with totals. Cost is shown only for model calls that have a price. |

A metric is either one of the [Insights](./insights.mdx) metrics, such as merge rate or build
duration, or a measurement a HIL test takes, such as motor overshoot. An Insights figure is the
same number the Insights page shows for the same days.

A window can be a length of time ending now (`7d`, `36h`, `2w`), a range of dates, or a
release's **baseline**: the measurements captured when that release shipped. Comparing a baseline
with the last week is the comparison the regression watch makes.

### When there is no data

If nothing was measured in a window, the tool says **no data** and names the window it searched.
It never reports zero for a window with nothing in it, and it never fills in days that had no
runs. A comparison with an empty side has no difference at all, and the brief says which side
was empty.

### Citing telemetry

Every answer is cited at a `telemetry://` address that holds the whole question:

| Answer | Example address |
| --- | --- |
| An Insights metric | `telemetry://metric/merge_rate/2026-09-11..2026-10-10` |
| A HIL measurement | `telemetry://case/<test case>/overshoot_pct/2026-10-03T02:47:47Z..2026-10-10T02:47:47Z` |
| A comparison | `telemetry://case/<test case>/hover_drift_cm/baseline:v2.0.4-vs-2026-10-03T02:47:47Z..2026-10-10T02:47:47Z` |
| A suite's history | `telemetry://history/suite/2026-09-10T02:47:47Z..2026-10-10T02:47:47Z?suite=PHYSICAL%20%C2%B7%20HIL%20rig` |
| Runs per day | `telemetry://runs/runs/2026-10-03T02:47:47Z..2026-10-10T02:47:47Z` |

The dates in an address are always exact. If an investigation asks for "the last 7 days", the
citation records the seven days that meant at the time, so reading the address again next month
asks about the same week. An investigation only ever reads your own workspace's numbers.

## Regression watch

The **regression watch** compares each night's measurements with the last release, and acts
when a metric has got worse. It involves no model: it reads numbers, builds commits on the
build farm, and writes down what it found. <Since version="0.41.9" module="ouroboros-rest" />

:::info[Read the watch through the API for now]

The **Regression watch** card arrives in a later release. Until then the watch is read from the
[REST API](../cli/rest-api.mdx) at `/api/v1/research/regression-watch`, which everyone in the
workspace may read. An Owner or a Maintainer sets it up — see
[Regression watch](../administration/research.mdx#regression-watch).

:::

### Baselines

A **baseline** is how a metric measured at a release: how many samples there were, their
median, how much they varied, and over which days. It is a measurement, so it is captured once
and never edited.

Baselines are captured in two ways:

- **On a release tag.** When a release is announced to Ouroboros, every watched metric of that
  repository is captured for it. Your deployment administrator connects the announcement — see
  [Announcing a release](../administration/research.mdx#announcing-a-release).
- **By hand.** An Owner or a Maintainer captures a release's baselines at any time.

A metric that had no measurements in its window gets no baseline: an empty window is not a
baseline of zero.

### The nightly comparison

Once a day the watch reads each watched metric over its last few days and compares that window
with the metric's newest baseline. A difference counts as **drift** only when all of these hold:

- the nightly window has enough samples;
- the metric moved by more than the baseline itself varied;
- it moved in the direction that is worse — a boot time that got faster is not a regression;
- it moved by at least the metric's warning threshold.

Anything less opens nothing. The thresholds have defaults per kind of metric, and your
workspace can tune them — see [Thresholds](../administration/research.mdx#thresholds).

### Drift and severity

Drift opens a **watch item**. It shows the signed drift in the unit you would say it in:

- a timing in its own unit — `+230 ms`;
- a percentage metric in points;
- anything else as a percentage of its baseline — `+14%`.

Its severity is **warn** from the warning threshold and **err** from the error threshold. If a
later night reads the metric back inside its thresholds, the item's severity becomes **ok** and
the item carries on where it was.

A metric has at most one open item. A night that reads the same drift again updates that item;
it does not open a second.

### What a bisect does and shows

When a metric has a **replayable test**, the watch finds the commit that caused the drift. It
runs a bisect between the release and the nightly: each step builds one commit on the build
farm and runs the metric's test, and the result decides which half to search next. A bisect
over 12 commits takes at most four farm jobs.

When the bisect finishes, the item shows:

- the **culprit** commit, as `bisected → a41f2c9`;
- the **farm jobs** that decided it, so you can open each one.

The watch does not guess. An item stays **detected** with a note that begins `needs repro` when:

- the metric has no replayable test;
- a release tag or the nightly ref names no commit;
- the bisect ends without isolating a commit — a job was cancelled, or every commit passed.

### From a culprit to a merged fix

After a bisect the watch does two more things without being asked:

1. It **opens a Regression forensics investigation**, already holding the comparison and the
   bisect as cited sources. If the investigation cannot be started, it stays queued with that
   evidence.
2. It **drafts a fix ticket** in Planning, with the drift, the culprit, the farm jobs and how to
   reproduce it. See [Planning](./planning.mdx).

The draft waits for you to file it. Your workspace can opt in to having the watch file and
queue it instead — see [Policies](../administration/research.mdx#policies).

From there the item follows the fix, and its status says where it is:

| Status | What the item shows |
| --- | --- |
| **detected** | The drift, and a `needs repro` note when it cannot be bisected |
| **bisecting** | A bisect is running on the build farm |
| **bisected** | `bisected → a41f2c9` |
| **investigating** | The culprit, and the forensics investigation — `forensics RS-131` |
| **queued** | `fix ticket drafted · FIX-1` while it is a draft, then `fix ticket drafted · #517` once it is filed as a ticket |
| **fixing** | `fix loop running · #512` — a loop is working on the ticket |
| **✓ merged** | `root-caused, fixed & merged · PR #641` |
| **dismissed** | An Owner or a Maintainer dismissed the item, with a reason |

### Hearing about drift

The watch files a decision in [Needs You](./inbox.mdx) twice for each item: once when it
detects the drift, and once when the bisect names a culprit. Each links to the watch, and an
Owner or a Maintainer can **Dismiss drift** from it with a reason. A decision closes by itself
once the item has moved on.

Dismissing an item cancels a bisect that is still running. The investigation and the draft it
produced are kept.

## Reading a brief

A **brief** is an investigation's answer. An investigation that finishes delivers one, and the
brief is made of the same parts whatever the question was:

- **findings**, each followed by the sources that back it;
- **open questions**: what the investigation could not back with a source;
- the **sources** it read, numbered;
- for a **Gap analysis**, a **capability matrix** and the tickets it proposes.

### The brief card

The **Featured brief** region of the Research page shows the newest finished investigation's
brief — the newest with **✓ brief ready**, or, if none, the newest with **✓ issues filed**. When
nothing has finished yet the region says *No brief yet*. <Since version="0.147.0" module="ouroboros-ui" />

<Screenshot id="user-guide.research.brief" />

The card's head names the investigation: its kind, its number and title (`RS-127 — AUTONOMOUS
DOCKING VS. THE FIELD` — the matrix's title for a gap analysis, the question for any other
kind), how many sources it read and at what depth, and its status. Beside them sit the two
actions, [**Export brief ↗**](#exporting-a-brief) and, for a gap analysis that proposes work,
[**Draft epic from gaps →**](#draft-epic-from-gaps).

Under the head, a gap analysis shows [its matrix](#the-capability-matrix) and then the brief's
text; every other kind shows the text alone. Beside them sit [the sources](#sources) the text
cites, the [proposed tickets](#proposed-from-gaps), and a **Led to:** row naming what the
investigation produced — a *fix draft* or *drafted tickets* (which open in Planning), a *roadmap
document* (which opens the **Roadmap pipeline** region), the *open run →* fixing what it found,
the *evidence →* run, or a forensics brief's *culprit*.

A brief can also be read from the [REST API](../cli/rest-api.mdx), at three addresses under
`/api/v1/research/investigations/<investigation id>`:

| Address | What it returns |
| --- | --- |
| `/brief` | The brief: its paragraphs and citations, the sources it cites, the capability matrix and the proposed tickets |
| `/sources` | Every source the investigation read, with its excerpt and when it was retrieved |
| `/brief/export` | The brief as a [Markdown file](#exporting-a-brief) |

Everyone in the workspace can read all three. An investigation that has not finished answers
`/brief` and `/brief/export` with `404 brief_not_found`; `/sources` already lists what it has
read so far.

### Findings and open questions

A brief's text is a series of claims. Each one is either:

- a **finding**: a claim backed by at least one source, which is named right after it; or
- an **open question**: something the investigation asked, or wanted to say, and could not
  back. It carries no source.

A claim is never shown as a finding without a source. If the investigation writes one it cannot
cite, the claim is kept as an open question and marked `demoted`, so you can see what it wanted
to say and that it could not prove it. Open questions are kept apart from the findings: on the
card they sit in their own inset block under **Open questions**, each in italics with its mark
(*open question*, or *demoted*); in the API each claim says which it is; and in the exported
file they sit under their own heading.

### Citations

A citation is a marker in square brackets after the claim it backs:

> The docking gap is not sensors: our IMU and rangefinder match Skylink's published
> spec.`[07]` It is control — Skylink runs a wind-feedforward MPC in the final 2 m`[12][31]`
> while ours is PID with fixed gains (`dock_ctrl.c:214`, unchanged in 14 months).`[git]`

- `[07]` is source number 7 of this investigation. Numbers below ten are written with two
  digits.
- `[git]` is a source with a name instead of a number. It names the line of code the claim is
  about.
- `[12][31]` is one claim backed by two sources.

**A source keeps its number.** Sources are numbered once, in the order the investigation read
them, and are never renumbered. `[07]` means the same source in the brief's text, in the list
of sources, in a matrix cell and in the exported file, today and next month. You can quote a
citation in a review without it going stale.

A reference to code, like `dock_ctrl.c:214` above, is shown in a fixed-width font and links to
that file at the exact commit the investigation read. Only a file one of the claim's own
sources cites is treated this way.

**On the card, every marker is a link.** Click `[07]` and the sources panel scrolls to source 7
and highlights its row. A marker in a matrix cell whose source no claim cites is not in the
panel, so clicking it opens the [full ledger](#sources) on that source instead.

### Sources

A brief lists the sources its own claims cite. Each has its marker, a title and where it came
from:

| Marker | Title | From |
| --- | --- | --- |
| `[07]` | Skylink S4 docking module — teardown & sensor BOM | `droneanalysts.example.com/s4-teardown` |
| `[19]` | Churn interviews Q2 — 9 of 14 cite docking reliability | `issue-index://support/churn-2026-q2` |
| `[git]` | dock_ctrl.c blame — gains last tuned 14 months ago | `helios-firmware @ 8c1b2e4 · src/dock/dock_ctrl.c` |

A web page and a file of code link to where they can be opened. A source inside Ouroboros, such
as a set of tickets or a telemetry reading, shows its address and has no link.

The full list holds every source the investigation read, including those no claim cites. On
the card, **all ↗** in the panel's corner opens it as a sheet — every record in number order,
the ones a claim cites marked — and `/sources` answers the same list. Each entry adds:

- the **excerpt**: the part that was read, saved at the time. It stays the same when the page
  it came from changes or disappears;
- **when it was retrieved**, in UTC.

Press Escape, or click outside the sheet, to close it.

### The capability matrix

A **Gap analysis** also delivers a matrix: one row for each capability, one column for your
product and one for each competitor.

| Cell | Meaning |
| --- | --- |
| `● shipping` | It is released |
| `◐ partial` | Part of it is there. A note may say more, such as `◐ beta` |
| `◐ in flight` | It is being built now |
| `○ none` | A source shows it is absent |
| `? unknown` | The investigation did not find out |

Every cell except `? unknown` cites at least one source. `? unknown` is an honest answer, not a
blank: it does **not** mean the competitor lacks the capability.

<Screenshot id="user-guide.research.matrix" />

On the card your own column comes first, headed `Helios (us)` and set in the accent. **Hover a
cell, or move the keyboard focus to it, to see its sources** — how many, and each marker, which
you can click to go to the source. A `? unknown` cell shows its note instead: *The investigation
did not find out. Not a blank, and not none.* Hover a gap chip to read how the gap was reached.
The matrix scrolls sideways in its own box when it is wider than the card.

The last column is the **gap**: how far behind the best competitor you are on that row.

| Gap | When |
| --- | --- |
| `WIP` | Yours is in flight |
| `LEAD` | You are ahead of every competitor whose status is known |
| `LOW` | You are level with the best competitor, or nothing can be measured because your own status or every competitor's is unknown |
| `MED` | You are one step behind the best competitor |
| `HIGH` | You are two steps behind: the best competitor ships it and you have none. Also one step behind, when the investigation judged the gap serious |

The steps are `none`, then `partial`, then `shipping`. A competitor whose cell is `? unknown` is
left out of the comparison.

The investigation proposes a gap for each row, and Ouroboros checks it against the cells. The
proposal only decides between `MED` and `HIGH` when you are one step behind. Anywhere else the
cells decide, and a proposal they do not support is overruled. Each row stores how its gap was
reached, for example:

> Helios: partial · best rival: shipping (Skylink) · rivals: 1 shipping, 1 partial, 1 none ·
> proposed: high · one step behind the best rival, proposed high → high

### Proposed from gaps

A gap analysis also proposes the work that would close its gaps: one **epic** and a list of
**tickets**, each naming the row it closes.

> EPIC · Docking parity · DOCK-1 wind-feedforward MPC · DOCK-2 re-planned retry · +3 more · L

- Only tickets for a `HIGH` or `MED` row are proposed. A ticket for a row where you lead, or
  one already in flight, is left out.
- The first two tickets are named and the rest are counted, as `+3 more`.
- The letter at the end is the **effort** of the whole epic. Each ticket's size is worth points
  (`XS` 1, `S` 2, `M` 3, `L` 5, `XL` 8). The points are added up and read back as a size: up to
  1 is `XS`, up to 3 `S`, up to 8 `M`, up to 20 `L` and more than that `XL`. The epic is never
  smaller than its largest ticket.

Nothing is filed. These are proposals for you to review.

### Draft epic from gaps

**Draft epic from gaps →** turns the proposal into drafted tickets in
[Planning](./planning.mdx). <Since version="0.41.10" module="ouroboros-rest" />

It creates:

- one **epic**, named as the brief named it and marked **proposed** on the roadmap;
- one **drafted ticket** for each proposed ticket, in one batch under that epic.

Each drafted ticket says which gap it closes and lists the sources behind it:

```md
Closes the **Wind-compensated docking** gap (HIGH) found by RS-127.

Proposed effort: M — a seed from the brief; the estimate is the sizer's.

**Sources**
- [07] Skylink firmware 6.2 release notes — `skylink.example.com/releases/6.2`
```

**Nothing is filed in your tracker.** The batch opens in Planning at `/planning?batch=…`, where
you review it, let the estimator size it, and push it when you are ready — see
[Reviewing the drafts](./planning.mdx#reviewing-the-drafts). The effort the brief proposed is
only a starting note; the size on each draft is the estimator's.

Drafting twice does not create a second epic: asking again answers the batch that was already
drafted.

On the card, press **Draft epic from gaps →** in the head. The page then opens Planning on the
batch. If your workspace has more than one ticket source, a dialog first asks **Which tracker are
the drafts for?** — choose one and press **Draft here**. The button is only shown for a brief
that proposes tickets.

Owners, Maintainers and members can draft; a Viewer cannot — on the card the button is switched
off for a Viewer, with the reason as its tooltip.

:::info[Draft through the API for now]

The button arrives with the brief card in a later release. Until then, send the request to the
[REST API](../cli/rest-api.mdx):

```bash
curl -X POST "$OURO_URL/api/v1/research/investigations/$INVESTIGATION_ID/draft-epic" \
  -H "content-type: application/json" -b cookies.txt -d '{}'
```

The answer's `href` is the Planning address of the batch.

:::

### Exporting a brief

**Export brief ↗** on the card — or `/brief/export` in the API — downloads the brief as one
Markdown file, named after the investigation, for example `RS-127-brief.md`. Use it to paste a
brief into a document review with its evidence attached. The download is the service's own
file, citations intact; nothing on the page is rewritten into it.

The file holds, in order:

1. the investigation's number and question, then its kind, depth, source count and brief
   version;
2. **Brief**: the text, with each citation marker after its claim, then **Open questions** as a
   list;
3. **Capability matrix**: a table whose cells carry their citations, then how each gap was
   reached (gap analysis only);
4. **Proposed from gaps**: the epic and every ticket (gap analysis only);
5. **Sources**: every source on its own line, with its marker, title, address and the time it
   was retrieved;
6. a **provenance** line: the investigation, the researcher that wrote the brief, the model
   alias it ran on, the brief's version and its date.

```md
## Sources

- [07] Skylink S4 docking module — teardown & sensor BOM — `https://droneanalysts.example.com/s4-teardown` — retrieved 2026-10-07T12:07:00.000Z

---

_Provenance: investigation RS-127 · researcher loop-v1 · alias researcher-long-ctx · brief v1 · 2026-10-07_
```

The markers in the file are the same as everywhere else, so a citation you quote from the file
points at the same source. Exporting the same brief twice gives the same file.

## From a brief to a roadmap to issues

A **roadmap investigation** can go further than its brief: Ouroboros turns the brief into a
`ROADMAP.md`, proposes the file to your repository, and files its items as issues.
<Since version="0.41.10" module="ouroboros-rest" />

```text
brief → create-roadmap → ROADMAP.md → pull request
                              ↑ suggested changes: Apply re-runs create-roadmap
ROADMAP.md → create-issues → drafts → sized → issues → written back into ROADMAP.md
```

:::info[Use the API for now]

The pipeline card arrives in a later release. Until then every step below is a request to the
[REST API](../cli/rest-api.mdx), under
`/api/v1/research/investigations/{investigationId}/roadmap`. Everyone in the workspace can read
a roadmap with `GET` on that address.

:::

### Who can do what

| Step | Who |
| --- | --- |
| Read the roadmap | Everyone in the workspace |
| Suggest a change, run a drift check | Owners, Maintainers and members |
| Generate the roadmap, apply or dismiss a suggestion, file the issues | Owners and Maintainers |

### Generating the roadmap

`POST …/roadmap` runs the **create-roadmap** skill over the brief and stores what it writes as
**version 1**: milestones with target dates, and under each a list of items with an **MVP**
flag and an effort.

`ROADMAP.md` is produced from that version, never typed by hand:

```md
# Helios — Q4 Improvement Roadmap

## M1 · Docking parity — target Oct 15
- [x] #742 Wind-feedforward MPC in final approach `MVP` `L`
- [ ] #743 Re-planned abort & retry vectors `MVP` `M`
```

An item shows its issue number once it has one, a tick once that issue is closed, `MVP` when it
is in the MVP set, and its effort.

An investigation has one roadmap. To change it, suggest a change; asking to generate it again
is refused.

- If your workspace has more than one ticket source, send `targetSourceId` to say which
  repository and tracker the roadmap is for.
- The file is written to `docs/ROADMAP.md`. Send `path` to put it somewhere else. The path
  cannot be changed afterwards.

**create-roadmap** and **create-issues** are skills on the
[Knowledge](./knowledge.mdx#the-roadmap-pipelines-skills) page. The version your workspace has
published is the one that runs.

### The file in your repository

Ouroboros does not write to your default branch. It commits `ROADMAP.md` to a branch of its
own, `ouroboros/roadmap-…`, and opens a **pull request**. Every later version goes onto the
same branch and updates the same pull request.

The roadmap's `projection` says where the file stands:

| State | What it means |
| --- | --- |
| `pending` | Not in the repository yet. `problem` says why, for example the repository refused the token. |
| `pr_open` | A pull request is open; `prRef` is its number |
| `committed` | The pull request was merged; `committedSha` is the commit |
| `drift_detected` | The file or the tracker no longer matches the roadmap — see [Drift](#drift) |

A roadmap is kept even when the repository cannot be reached. It stays `pending`, and the next
drift check tries again.

While your workspace is in [dry-run](../administration/policies.mdx#dry-run), the pull request
is opened as a draft.

An Owner or a Maintainer can let Ouroboros commit straight to the default branch instead — see
[Committing without a pull request](../administration/research.mdx#committing-without-a-pull-request).
It is off unless they turn it on.

Do not edit `ROADMAP.md` by hand. The next version would replace your edit, and the drift check
reports it.

### Suggested changes

Anyone who can draft can suggest a change with `POST …/roadmap/suggestions`:

```json
{ "text": "Pull the gust estimator into the M1 MVP set." }
```

A suggestion waits, **open**, until an Owner or a Maintainer settles it:

- **Apply** (`POST …/suggestions/{suggestionId}/apply`) runs **create-roadmap** again, with the
  current version and every suggestion applied so far. What it writes is stored as the next
  version, and the suggestion records which version it produced. The pull request is updated.
- **Dismiss** (`POST …/suggestions/{suggestionId}/dismiss`) closes it and changes nothing. The
  dismissal is recorded in the audit log.

Applying a suggestion never edits the roadmap in place. Each version is kept as it was written,
so you can see what every suggestion changed.

Ouroboros raises suggestions too. They are marked **AI** and name what raised them, for example
`drift-detector`. They are applied and dismissed the same way.

A suggestion cannot be edited or settled twice. Write a new one instead.

:::warning[Applying a suggestion does not change issues that are already filed]

Once the roadmap's issues are filed, a new version changes `ROADMAP.md` only. If a suggestion
retitles an item or changes its MVP flag, change the issue in your tracker as well. Until you
do, the drift check reports the difference.

:::

### Filing the issues

`POST …/roadmap/issues` runs **create-issues**. Each call does as much as it can and says where
it stopped in `stage`. Send it again until it answers `filed`.

1. **Drafted.** The **create-issues** skill writes a description for every item, and the items
   become one batch of drafted tickets in [Planning](./planning.mdx). Each draft is filed under
   its milestone and carries the label `mvp` when the item is in the MVP set.
2. **Sized** — `stage: "sizing"`. The estimator sizes the drafts, as it sizes every batch.
   Nothing is pushed while it works. Send `{"pushUnsized": true}` to push without waiting.
3. **Pushed.** The batch is pushed to your tracker. A milestone that does not exist yet is
   created with the roadmap's target date as its due date. A milestone that already exists
   keeps its own date.
4. **Written back** — `stage: "filed"`. The issue numbers go into a new version of the roadmap,
   and the pull request is updated. The investigation's status becomes **issues filed**.

`stage: "partial"` means the push stopped before every draft was filed, for example because the
tracker limited the rate. Send the request again to continue.

Filing twice is safe. A draft that was pushed is never pushed again, and a call that has nothing
new to record writes no new version.

Each filed item then shows its issue, and the estimator's figures for it: effort, complexity and
the estimated loop time in **loop-days**.

An item added by a later suggestion, after the batch was drafted, is listed in `undrafted` and
is not filed by this request.

### Drift

A **drift check** compares the roadmap with your tracker and with the file in your repository.
Ouroboros runs one on a schedule, and `POST …/roadmap/drift-check` runs one now.

For every filed item it compares three things with the issue:

- the **title**;
- whether it is **done** — the issue is closed;
- the **MVP** flag — the issue carries the label `mvp`.

For a roadmap whose pull request was merged, it also compares the file in the repository with
the roadmap.

When something differs:

- the roadmap is marked `drift_detected`;
- **one** suggestion is raised, by `drift-detector`, naming every difference:

  > Tracker drift — #744 is done in the tracker and open in the document. Apply to regenerate
  > the roadmap from what the tracker and the repository now say.

Nothing is rewritten. The roadmap, the file and the issues are left as they are until you apply
or dismiss the suggestion. While that suggestion is open, another check raises no second one.

Applying the suggestion writes a new version that takes each item's done state from the
tracker.

The check also finishes what an earlier step could not: it retries a file that is still
`pending`, and it notices that a pull request was merged or closed.

## Investigations and the library

The **Investigations** card at the foot of the page lists the workspace's investigations —
the active ones by default, and every one in the library. <Since version="0.148.0" module="ouroboros-ui" />

<Screenshot id="user-guide.research.library" />

### The rows

The card's head counts the workspace: `4 active · 23 this quarter`. **Active** is every
investigation that did not fail and was not cancelled; **this quarter** is every investigation
started in the current calendar quarter, counted in UTC against the real quarter boundary, so the
number resets when the quarter turns.

Each row shows:

- the investigation's number, `RS-127`, and its kind as a chip in the kind's colour;
- the question, over a sub-line with the source count and the depth — `44 sources · deep dive`;
- a status pill: **queued**, **running**, **cancelling**, **✓ brief ready**, **✓ issues filed**,
  **failed**, **cancelled** — or **fix loop live**, for a finished bug investigation whose fix
  ticket has a loop running now. A pill pulses while something is running;
- the one link that matters for it, when it has one:

| Link | Where it goes | When |
| --- | --- | --- |
| **open run →** | The run console of the loop fixing what the investigation found | The fix ticket has a run in flight |
| **to roadmap →** | The **Roadmap pipeline** region | A roadmap document was generated from the brief |
| **brief ↑** | The **Featured brief** region for the featured investigation; the row's own brief for any other | The investigation delivered a brief |
| **evidence →** | The test results the investigation's evidence came from | A source measured a test run |

A **running or queued row is live**: its source count and pill update as the investigation works,
without a reload.

**Click a row's question** to open the investigation in place of the rows: a finished one shows
[its brief](#reading-a-brief), the same card as the featured brief; one that has not finished

the open investigation (`?open=…`), so it can be shared.

### History and the library

**History** in the card's head — and **Research library** in the page head — open the same
view: every investigation, newest first, with three filters that combine:

| Filter | Choices |
| --- | --- |
| **Kind** | All kinds, or one of the workspace's kinds |
| **Status** | All statuses, **Active**, or one status |
| **Quarter** | All quarters, **This quarter**, or one of the last eight quarters, `Q3 2026` |

The filters are written into the address — `/research?view=library&kind=gap_analysis&status=brief_ready&quarter=current` —

next page.

The card closes with the page's promise: *Every investigation ends the same way the build loop
does: with evidence — and, when you approve, with tickets the loop picks up next.*
