Every loop that works on an issue is a **run**, and every run has a **run console** at
`/runs/<id>`. It is where you watch a loop work, see why it stopped or failed, and — while it
runs — pause, steer or abort it. Open it from a loop on the [dashboard](../dashboard.mdx), the
Build Farm, Issues, Workflows, Knowledge or Insights; the breadcrumb at the top takes you back
to where you came from.

<Screenshot id="user-guide.run.live" />

## The header

The header names the loop and the issue it is working on — **Run Console · Loop #1847**, then
**#482 — Fix flaky CAN-bus telemetry test**, which links to the issue in your tracker. Below
it:

- **The status** — **coding**, **building** or **review** while the loop runs (the dot
  pulses); **merged**, **needs human**, **failed** or **canceled** once it has finished.
- **The workflow and version** the run is pinned to, such as **standard-fix v14** — the version
  that was published when the issue was queued (see
  [Which version runs](../workflows/studio.mdx#which-version-runs)).
- **The model** the run is routed to.
- **elapsed** — how long the run has taken; it keeps counting while the loop runs and stops
  when it finishes.
- **branch** — the branch the loop pushes to, with a button to copy its name; **no branch
  yet** until it has pushed one.
- **PR verification** — once the loop has opened a pull request, a link to its
  [verification page](../pull-requests.mdx). A merged run also links to the pull request
  itself, such as **PR #512 ↗**.

A run opened by the run simulator — a test tool used in development and testing — carries a
**Simulated run.** note: nothing real did the work it shows. A run from simulated or demo data is also labelled **Simulated** or
**Demo data** beside its title — see
[Where the data comes from](../concepts.mdx#where-the-data-comes-from).

## The stage timeline

The **Stage timeline** shows the workflow's stages in order, each marked **✓** done (with how
long it took), **●** in progress, **○** pending, **✕** failed or **–** skipped. A stage the loop
is repeating shows its attempt — **attempt 2/3** — and a note says why it went round again,
such as **attempt 1 failed tests — loop returned from gate ↺**.

The stages come from the version the run is pinned to, so they stay the same even if the
workflow is edited and published again while the run is going.

**If the engine restarts mid-run**, the run picks up again on its own, usually within half
a minute. It carries on from its last completed stage, and its working tree is put back to
how that stage left it. The stage that was interrupted runs again as its next attempt, so
you may see **attempt 2/3** on a stage that did not fail.

Select a stage to show only its entries in the transcript; select it again, or choose
**Show all**, to see everything. Once the loop reaches its test stage, **Test results ↗** on
that stage opens the run's [test results](./tests.mdx).

### Build stages

A build stage runs on your [Build Farm](../../administration/build-farm.mdx), in the runner pool the stage
names. Under the stage, the timeline shows the farm job and where it really is, such as
**#483 · building on forge-02**:

- **waiting for a runner in pool-a** — the job is queued in the pool.
- **offered to forge-02**, then **accepted by forge-02** — a runner is taking it.
- **building on forge-02** — the runner is running the build.
- **exit 0 · ccache 78.4%** or **exit 2** — the build finished, with its exit code and, when
  it was measured, its ccache hit rate.

The transcript says the same as it happens: **Build #483 is running on forge-02.**, then
**Build #483 passed on forge-02 (exit 0 · ccache 78.4%).** **Build log ↗** under the stage
opens the build's whole log over the console, without leaving the run.

The build's exit code decides the workflow's gate. When the build passes, the loop moves on.
When it fails, the loop skips the stages before the gate and the gate sends it back the way
the workflow says, usually to **Implement**. The next attempt then shows a note such as
**attempt 1 failed the build — loop returned from gate ↺**. The gate's verdict appears in the
transcript with the exit code and ccache result it decided on.

## The agent transcript

The **Agent transcript** is what the loop did, entry by entry, each with its time and who
wrote it:

- **PLAN** — what the loop intends to do next.
- **TOOL** — an action: reading or editing a file (with the diff), running a command or the
  tests (with the result, and a progress bar while they run).
- **The model's name**, such as **CLAUDE-FABLE-5** — the model's reasoning.
- **GATE** — a decision the workflow took, such as sending the loop back to an earlier stage.
- **USER** — a note someone sent with **Steer the loop**.
- **SYSTEM** — the platform's own notes.

While the loop runs, the card is marked **streaming** and new entries appear at the bottom; it
follows them unless you scroll up, when **Jump to latest ↓** takes you back. **Raw JSONL ↗**
downloads the whole transcript. The card keeps the most recent entries; for a very long run,
a note says how many earlier ones are only in the download.

## Changes, resources and guardrails

Beside the transcript:

- **Changes so far** — the files the loop has changed, with lines added and removed, its
  commits, and how the pull request will be merged (**will squash on merge**).
- **Resources** — what the run has used: **Tokens** against the run's token budget
  (**212k / 400k budget**), **Est. cost** against the spend cap (**$1.14 / $2.50 cap**), the
  **Build farm** runner it holds, and **Wall clock**. A cost shown as **—** means the model has
  no price set; Ouroboros does not guess one.
- **Guardrails** — the checks every change must pass, one row each:

| Check | Passed | Failed |
| --- | --- | --- |
| Allowed paths | **Diff confined to allowed paths** | **Diff outside allowed paths** |
| CI configuration | **No CI config touched** | **CI config touched** |
| Secrets | **Secrets scan clean** | **Possible secret in the diff** |

A fourth row reports the review policy: **Human review not required** (auto-merge eligible),
or **Human review required** — either routed to a person, or, when it fails, because auto-merge
is not permitted for this change.

The card's tag sums them up: **clean**, **violations**, **pending** while a check is still
running, or **not evaluated**. When warning checks have failed too, the tag counts them
separately, such as **1 violation · 1 warning**, or **1 warning** when only warnings failed. A failed check opens its **Evidence** — the path, the rule and
the protected-path pattern it matched:

<Screenshot id="user-guide.run.guardrail" />

The secrets scan looks for known credential formats; a pass means none was found, not that the
diff holds no secret. Its **ⓘ** says so.

**Blocking and warning checks.** Each check either blocks or warns; an administrator chooses
which for the workspace (see [Policies § Guardrail checks: block or warn](../../administration/policies.mdx#guardrail-checks-block-or-warn)).
Every check blocks unless it is changed.

- **A blocking check that fails** is marked **✗** with **blocked — the run needs a person**. The
  checks run each time the loop changes a file, so a live run **stops right after the tool call
  that caused the failure**, not at the end of the stage. The stage fails and the run moves to
  **needs human**, with the failed check and its evidence as the reason.
- **A warning check that fails** is marked **!** with **warn — did not stop the run**. The run
  carries on, and the failure stays on the card for whoever reviews the change.

A failed blocking check is a question for a person — answer it in [Needs You](../inbox.mdx),
where a one-time allowance can be granted. The console itself has no allow or override control.

## Controlling a live run

Owners and admins see three controls in the header while a run is live. A finished run has
none.

<Screenshot id="user-guide.run.controls" />

- **Pause loop** asks the loop to stop at its next safe point: between two tool calls, never
  in the middle of one, or between stages. A tag beside the controls
  follows the request — **Pause · sending**, **sent**, **received**, **acknowledged** — and
  once the loop has acknowledged, the button becomes **Resume**. If the loop does not answer,
  the tag reads **no response — run may be between stages**.
- **Take over in IDE** pauses the loop and shows you how to carry on by hand: the commands to
  check out its branch (**Copy commands**), and links to the ticket and the transcript. Press
  **Resume** when you want the loop back. Nothing opens in your editor by itself.
- **Abort run** stops the loop for good. It asks first — **Abort Loop #1847?** — and you type
  the loop number to confirm. The loop stops at its next safe point, between two tool calls,
  and keeps the work it has done so far on its branch; the run is marked **canceled**. This
  cannot be undone.

**Steering** is open to owners, admins and members: type a note in **Steer the loop** under
the transcript and choose **Send**. It nudges the current attempt without pausing it: the loop reads it before its next
model turn, and the acknowledgement names the attempt it landed on, such as **steering applied
to attempt 2** — for
example, `prefer a fix inside the ISR; do not touch the test timeouts`. Your note appears in the
transcript as a **USER** entry, with a tag that follows it to **acknowledged**. A note can be
up to 4,096 characters. Viewers can read the transcript but not steer.

## When a run needs you

A run that is waiting for a decision shows the status **needs human**: it has stopped, and the
console offers no controls or steering. A run gets there when its workflow reaches a
**hand it over for review** terminal, or when a blocking guardrail check fails. The question it is waiting on is in
[Needs You](../inbox.mdx) — answer it there and the loop carries on. The console does not link
to the question itself.

## Finished runs

<Screenshot id="user-guide.run.completed" />

Once a run has finished, its console is a record: the status is final, **elapsed** stops,
the transcript is no longer **streaming**, and the controls and the steer box are gone — the
steer box says **This run has ended, so there is no loop left to steer. The transcript stays
readable.** A merged run links to its pull request.

Older runs may hold less than the console can show — no stages or transcript entries recorded,
as in the example above — in which case the cards say so rather than showing nothing.

## What can go wrong

- **"No new activity since … — the run's events have gone quiet."** Nothing has arrived for
  more than two minutes. The loop may be paused, working on something long, or the events may
  have stalled. Choose **Check again**; what is shown may be out of date.
- **"This run could not be read."** The console could not reach the service. Choose
  **Retry**; while it retries, the page keeps what it last showed.
- **"This run does not exist."** The link is mistyped, or the run belongs to another
  workspace. Check the workspace in the header.
- **A control stays at "sent".** The loop has not picked it up yet — it answers between
  stages. If it expires with **no response**, try again.
- **"No runner in pool `pool-a` can take this build …"** No runner in the stage's pool is
  online, free and set up for the pool's executor. The build was cancelled and the run fails
  at that stage. Bring a runner back on the [Build Farm](../../administration/build-farm.mdx) and queue the issue
  again. A build that waits ten minutes with no runner able to take it fails the same way.
- **"build_pool_required: stage `build` names no runner pool."** The workflow's build stage
  has no **Runner pool**. Set one in [Workflow Studio](../workflows/studio.mdx) and publish.
- **A build failed and the loop went back to Implement.** That is the workflow's gate doing
  its job — see [Build stages](#build-stages). If **Implement** has used all its attempts,
  the run fails, naming the gate and the build that failed.
- **"Build #483 was cancelled on the farm before it finished."** Someone cancelled the job on
  the Build Farm. The run fails at the build stage.
- **The run failed after "attempt 3/3".** The stage failed, or was refused a tool call by its
  permissions, as many times as its **Max retries** allows. The transcript shows the last
  refusal or error.
- **The controls are missing.** The run has finished, or you are not an owner or admin.
- **"Type the loop number to enable the abort."** The number you typed does not match the
  loop; type it exactly, with or without the **#**.
