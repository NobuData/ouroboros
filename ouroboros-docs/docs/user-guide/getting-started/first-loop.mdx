You chose **Run my first loop →** in the [Get Started wizard](./wizard.mdx). This page
follows that loop from the queue to its draft pull request.

## Before you start

A live loop needs more than any one screen shows. Before it starts, Ouroboros checks each
prerequisite for your repository and workflow. Each item passes, fails, or is **unknown**
(Ouroboros could not confirm it), with a reason and a link to where you fix it:

| Item | What it means |
| --- | --- |
| Live execution | The deployment allows live loops. An operator turns this on — see [Live execution](../../administration/live-execution.mdx). |
| Workspace | The workspace is active, not paused or pending deletion. |
| Provider connection | An enabled provider connection can serve the loop's model calls, and passed its last test. Never tested is unknown: test it under <UiPath path="Models > Providers & keys" />. |
| Routes | Every task kind the workflow uses has a route to a model, and that model has a price, so the run's spend can be capped. |
| Stage executors | The engine has a stage executor registered for the workflow's model stages. |
| Runner | Each build stage names a runner pool, and that pool has a runner online that can check out the repository. |
| Repository | The repository is enabled for the loop. |
| Push permission | The workspace's GitHub token can push a branch to the repository. |
| Pull-request permission | The GitHub source that mirrors the issue can open a pull request in the repository. Until a first issue is picked, this is unknown. |
| Dry-run | The repository is in dry-run, so the pull request opens as a draft and nothing merges. |
| Workflow | The workflow has a published version Ouroboros can read. |
| Concurrency | A live-run slot is free under the workspace's ceiling. |

GitHub reports what the token's **account** may do, not the token's own scopes. A passing
permission item confirms everything GitHub can tell Ouroboros, and nothing more.

The wizard shows this list on its last step as **Ready to run?** — see
[the wizard's step 4](./wizard.mdx#ready-to-run). The loop is ready only when every item
passes. While live execution is on, **Run my first loop →** stays disabled until it is, with
the first item to fix as its caption. With live execution off, the action is **Finish setup**:
it queues the issue, which waits until an administrator turns live execution on.

Beside the list is an **estimate**, and it is labelled as one: the per-run cost cap of the
loop's model route, and the size the estimator gave the picked issue. It is not a promise of
time or cost, and it never decides whether the loop is ready.

Checking reads only. It never calls a model, starts a job or changes anything, so it is safe
to check as often as you like.

## Where it appears

1. **In the queue.** The issue waits in **Up next in queue** on the
   [dashboard](../dashboard.mdx) — the wizard's **See it in the queue →** takes you there —
   until a loop picks it up.
2. **In Active loops.** Once a loop claims it, it moves to **Active loops** on the
   dashboard, and the header's live-loop count goes up. Open the row — or the wizard's
   **Open the run console →** — to watch it in the [run console](../runs/console.mdx).
3. **In the run console.** The stage timeline shows each stage as it starts and finishes;
   the agent transcript shows what the loop is reading, planning and changing; the side
   column shows the changes so far, the resources used and the guardrails, including the
   protected paths you saved in the wizard.
4. **As a draft pull request.** When the work passes its build and tests, the loop opens a
   **draft** pull request. Its verification page shows the gates it passed and the
   acceptance criteria it was checked against — see
   [Pull requests](../pull-requests.mdx).
5. **In the recently closed list.** When the loop finishes, the dashboard lists it among the
   work recently closed by the loop.

There is no separate tour: the wizard's receipt card, the dashboard and the run console are
where you follow it.

**Your first loop is a real one.** Ouroboros never stands a simulated run in for it. If this
deployment cannot run loops yet, the issue waits in the queue and the dashboard says why,
rather than showing you a loop nothing really ran.

## What to do while it runs

- **Answer it if it asks.** If the loop needs a decision, it waits in
  [Needs You](../inbox.mdx), with a count in the sidebar and the header.
- **Steer it.** In the run console you can send the loop a note with **Steer the loop**.
- **Review the draft.** Dry-run keeps the pull request a draft and Ouroboros refuses to
  merge it — read it to judge the loop's work. When you trust the loop to merge, an owner or
  admin turns dry-run off under <UiPath path="Settings > Policies" /> — see
  [Concepts](../concepts.mdx#dry-run-and-live).

## What can go wrong

- **The issue stays in the queue** — no loop has picked it up yet; issues ahead of it in
  **Up next in queue** go first. The wizard's receipt says so until a loop claims it.
- **The loop stops and waits** — it needs a decision; open [Needs You](../inbox.mdx).
- **The loop goes back to an earlier stage** — a build or test failed and it is trying
  again; the stage timeline shows the attempt, and [test results](../runs/tests.mdx) show
  why.
- **The pull request never merges** — that is dry-run working as intended.
